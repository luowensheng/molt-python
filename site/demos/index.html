🔥 Mojo performance

Mojo SIMD vectorization

Shows exactly where Mojo's speed advantage comes from: SIMD types that process 8 float32 values per CPU instruction, without GIL overhead. Benchmarks a 1-million-element addition against a pure Python loop — the gap is stark.

What you'll see

  • Manual SIMD while-loop (WIDTH=8 float32)
  • Hardware SIMD width detection at runtime
  • ~40–50× speedup over Python loop
  • Scalar Mojo vs SIMD Mojo comparison too

Available tasks

  • molt run simd — SIMD vs Python benchmark
  • molt run bench — full timing suite

Core SIMD pattern

alias WIDTH = 8  # 8× float32 = 256-bit (AVX2)

fn add_vectors(a: DTypePointer[DType.float32],
               b: DTypePointer[DType.float32],
               c: DTypePointer[DType.float32], n: Int):
    var i = 0
    while i + WIDTH <= n:
        # Load 8 floats, add them, store 8 floats — one CPU instruction
        c.store(i, a.load[WIDTH](i) + b.load[WIDTH](i))
        i += WIDTH
    while i < n:  # scalar tail
        c.store(i, a.load(i) + b.load(i))
        i += 1

Mojo matrix multiplication

Three implementations of N×N matrix multiplication in increasing order of optimization: naive O(N³) triple loop → SIMD-vectorized inner loop → cache-friendly tiled + parallelized. Benchmarked against numpy (MKL) at N=128. The tiled variant reaches ~85% of numpy's throughput.

Implementations

  • Naive: baseline triple-loop, 120 ms at N=128
  • SIMD: vectorized inner loop, 18 ms (6.6× vs naive)
  • Tiled+parallel: 6 ms (20× vs naive, ~85% of numpy)
  • numpy MKL reference: 4 ms

13
⚙️ C extension Python ↔ C zero boilerplate

C extension module — header-driven, bidirectional

First-class C extensions with zero manifest boilerplate. Declare [[tool.molt.c.modules]] in pyproject.toml, point at a .h header, and molt sync auto-parses every scalar function signature, generates a full CPython PyInit_ / PyMethodDef module (not ctypes!), and compiles via zig cc. The relationship is bidirectional: Python calls C at native speed, and C can call back into Python packages via PyImport_ImportModule — the full molt package store is on PYTHONPATH.

What you'll see

  • Header parsed → PyInit_fastmath generated automatically
  • 8 functions: arithmetic, statistics, integer ops
  • Real CPython extension — not a ctypes wrapper
  • zig cc: macOS, Linux, Windows, no extra toolchain
  • Cached in ~/.molt/native/ — instant on unchanged source
  • C code can call PyImport_ImportModule("numpy") — it's on PYTHONPATH

Available tasks

  • molt sync — parse header + compile .so
  • molt run demo — call all 8 functions from Python
  • molt run bench — C extension vs Python
  • molt c build — explicit rebuild
  • molt c list — show discovered modules

The entire config (pyproject.toml)

# That's it. No setup.py, no .pyx, no ffi.cdef().
[[tool.molt.c.modules]]
name = "fastmath"
src  = ["fastmath.c"]
# headers defaults to fastmath.h — auto-discovered from src directory

[tool.molt.tasks]
demo  = "python main.py"
bench = "python bench.py"

Python calling C — zero glue code

/* fastmath.h — molt parses this, generates all PyArg/PyInit boilerplate */
double add(double a, double b);
double clamp(double value, double lo, double hi);
double lerp(double a, double b, double t);
int    gcd(int a, int b);
double variance3(double a, double b, double c);

# Python side — import and call like any module
import fastmath
print(fastmath.lerp(0.0, 100.0, 0.25))    # → 25.0
print(fastmath.gcd(48, 18))               # → 6
print(fastmath.variance3(2.0, 4.0, 6.0))  # → 2.666...

C calling Python — the full package store is available

/* Any C extension can call back into managed Python packages */
/* PYTHONPATH is already set to ~/.molt/pkg/... by molt sync  */
#include <Python.h>

static PyObject* call_numpy(PyObject* self, PyObject* args) {
    PyObject* list;
    if (!PyArg_ParseTuple(args, "O", &list)) return NULL;

    /* numpy is in the molt store — importable from C */
    PyObject* np   = PyImport_ImportModule("numpy");
    PyObject* arr  = PyObject_CallMethod(np,  "array", "O", list);
    PyObject* mean = PyObject_CallMethod(arr, "mean",  NULL);
    Py_DECREF(arr); Py_DECREF(np);
    return mean;   /* Python float → caller */
}

🌐 Polyglot 25 runtimes

Universal script launcher — run-handler system

molt run hello.rb dispatches to ruby hello.rb — no tasks, no config, no activation. Any file extension registered in ~/.molt/run-handlers.yaml is dispatched directly. 25 runtimes ship built-in and you can add your own in one command. All handlers support per-OS command overrides and the full token vocabulary.

What you'll see

  • 9 languages confirmed: Ruby, Node.js, Lua, Perl, Bash, Go, Swift, Julia, Elixir
  • Args forwarded verbatim: molt run hello.rb Alice
  • Polyglot table: all languages with timing via molt run all
  • Custom handler registration: molt run-handler add deno "deno run {file} {args}"
  • Cross-platform overrides: separate --windows command per extension

Available tasks

  • molt run hello.rb [name] — Ruby
  • molt run hello.js [name] — Node.js
  • molt run hello.go [name] — Go
  • molt run hello.jl [name] — Julia
  • molt run hello.exs [name] — Elixir
  • molt run all — all languages in a table
  • molt run-handler list — show all 25 built-ins

Dispatch order in molt run <arg>

# molt run checks, in order:
# 1. Flag-shaped arg → default entry
# 2. No arg         → main.py / python -m <pkg>
# 3. Ends in .py    → runPythonScript
# 4. Ends in .mojo  → mojo run
# 5. Has any ext + handler registered → runWithHandler  ← THIS DEMO
# 6. Matches task in [tool.molt.tasks] → task runner
# 7. Fallthrough    → exec binary on PATH

Managing handlers

molt run-handler list                         # all built-ins + user handlers
molt run-handler show rb                      # Extension: .rb  Command: ruby {file} {args}
molt run-handler add deno "deno run {file} {args}"
molt run-handler add ts "npx ts-node {file} {args}" --windows "npx.cmd ts-node {file} {args}"
molt run-handler remove deno
molt run-handler reset                        # restore factory defaults

Token reference

{file}      # absolute path to the script
{dir}       # directory containing the script
{basename}  # filename without extension
{args}      # extra arguments, space-joined
{python}    # project's pinned Python interpreter
{zig}       # auto-installed zig binary

⚙️ C project run + build Python ↔ C

C project management — run, build, orchestrate

molt as a complete C project manager — not C-as-a-Python-extension (that's demo 13), but C as the primary language. Two distinct capabilities: single-file run (molt run hello.c compiles with zig cc and executes immediately — no config, no Makefile) and multi-file project tasks (build, run, clean all via molt run <task>). Python orchestrates the C binary through subprocess, living in the same molt project.

What you'll see

  • molt run hello.c → compiles + runs in one command
  • molt run hello.c Alice → args forwarded after compile
  • molt run build → multi-file C binary (bin/stats)
  • molt run demo → Python drives C binary: 3 datasets + histograms
  • molt run clean → removes compiled artifacts
  • molt run-handler show c → inspect the zig cc compile template

Available tasks

  • molt run hello.c [name] — one-shot compile + run
  • molt run build — cc -O2 → bin/stats
  • molt run stats <nums...> — run the C binary
  • molt run demo — Python drives C: 3 datasets
  • molt run clean — remove compiled binaries

Single-file C — zero configuration

/* hello.c — no pyproject.toml needed for single-file run */
#include <stdio.h>
int main(int argc, char *argv[]) {
    const char *name = argc > 1 ? argv[1] : "World";
    printf("Hello from C! 👋 %s\n", name);
    return 0;
}

$ molt run hello.c          # Hello from C! 👋 World
$ molt run hello.c Alice    # Hello from C! 👋 Alice

How the .c handler works

# The built-in handler (inspect with: molt run-handler show c)
# Unix:    sh -c "{zig} cc -O2 -o {dir}/{basename} {file} && {dir}/{basename} {args}"
# Windows: cmd /c "{zig} cc -O2 -o {dir}\{basename}.exe {file} && {dir}\{basename}.exe {args}"

# Tokens resolved at run time:
{zig}      → /Users/.../.molt/toolchains/zig/0.14.1/zig  (auto-installed)
{dir}      → /path/to/15-c-project
{basename} → hello
{file}     → /path/to/15-c-project/hello.c
{args}     → Alice

Multi-file project — pyproject.toml tasks

# pyproject.toml — same format as any Python project
[tool.molt.tasks]
build = "cc -O2 -Wall -o bin/stats src/main.c src/stats.c -lm"
stats = "bin/stats"       # run the binary (pass args with: molt run stats 1 2 3)
demo  = "python demo.py"  # Python drives the C binary
clean = "rm -f bin/stats"

# Swap cc for zig cc for guaranteed cross-platform compilation:
# build = "zig cc -O2 -target x86_64-linux -o bin/stats-linux src/main.c src/stats.c"

Python orchestrating C

# demo.py — Python calls the C binary, lives in the same molt project
import subprocess
from pathlib import Path

BIN = Path(__file__).parent / "bin" / "stats"

result = subprocess.run(
    [str(BIN), "88", "92", "71", "95", "84"],
    capture_output=True, text=True

print(result.stdout)
