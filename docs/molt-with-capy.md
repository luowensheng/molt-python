# molt × Capy — what the product looks like

This document is a concrete before/after showing exactly what changes when Capy
is integrated into molt. Three surfaces change for users; one changes for driver
authors. None of it is theoretical — every example maps to real code paths in the
existing codebase.

---

## 1. `molt init` — rich scaffolding instead of string substitution

### Today

The template engine in `internal/templates/` is a hand-rolled mini-TOML parser that
does two things: rename `__pkg__` in file paths and replace `{{name}}`/`{{pkg}}` in
file contents. That's it. There's no validation, no conditional logic, no way to ask
the user questions and adapt the scaffold.

```
molt init my-api --template src
```

Applies a static directory tree. Every user gets the exact same files.

### With Capy

Each built-in template becomes a Capy library. `molt init` gathers answers to a
handful of prompts, serialises them as a Capy DSL source string, runs them through
the library, and writes the output files.

```
molt init my-api --template fastapi
```

```
? Python version: 3.12
? Port: 8000
? Include auth? yes
? Include tests? yes
? Database: postgres
```

Internally, molt builds:

```
# (never written to disk — constructed in Go from the answers)
name "my-api"
python "3.12"
port 8000
auth true
tests true
db postgres
```

The `fastapi` library generates from that:

```
pyproject.toml
moltproject.toml          ← tasks: dev, test, lint, migrate
src/my_api/__init__.py
src/my_api/main.py        ← FastAPI app, /health, /items skeleton
src/my_api/auth.py        ← JWT auth (only because auth = true)
src/my_api/db.py          ← asyncpg pool (only because db = postgres)
tests/test_main.py        ← pytest + httpx (only because tests = true)
.env.example
README.md
```

The `auth` and `db` sections of `main.py` appear only when the corresponding flags
are set — because the library's `file_template:` gates those blocks on `context.auth`
and `context.db`. Today that's impossible without branching the template into separate
files.

#### Custom org templates

```bash
molt template add my-org-api ~/.my-org/molt-templates/api.yaml
molt init payments-service --template my-org-api
```

`api.yaml` is a Capy library written by the org. It can add org-required boilerplate
(logging setup, `CHANGELOG.md`, internal linter config, Dockerfile, GitHub Actions
workflow) that the user never has to remember. Any team member can `molt template add`
it from a shared path; no binary change to molt.

#### Validation the current system cannot express

```yaml
# In the fastapi library
types:
  PythonVersion:
    options: ["3.10", "3.11", "3.12", "3.13"]
  Database:
    options: ["postgres", "sqlite", "mysql", "none"]
  Port:
    base: int
    pattern: "^[1-9][0-9]{3,4}$"   # 1000–99999
```

If the user types `python "3.8"`, the library rejects it at parse time with:
```
init error: arg "python_version": value "3.8" is not in options for type
"PythonVersion": [3.10 3.11 3.12 3.13]
```

Today that error doesn't exist — you get a broken project.

## 2. `<name>.capy.toml` — user-defined code generation targets

This is entirely new. It mirrors `<name>.molt.toml` for glue, but for any
Capy-powered code generation step the user wants to add to their project.

### The manifest

```toml
# api.capy.toml  (sits alongside moltproject.toml)
library = "targets/fastapi/lib.yaml"
src     = "api.capy"
out     = "src/generated/routes.py"
```

```toml
# schema.capy.toml
library = "targets/sqlalchemy/lib.yaml"
src     = "schema.capy"
out     = "src/generated/models.py"
```

`molt sync` picks up every `*.capy.toml` in the project directory (same scanner
that finds `*.molt.toml`), runs `capy run <library> <src> --out <out>` for each,
and places the generated files where they belong before Python packages are installed.

### What the user actually writes

```
# api.capy  ← the user's source of truth

resource users
    columns id:int name:str email:Email created_at:datetime
    auth required
end

resource posts
    columns id:int title:str body:text author_id:int
    auth optional
end

route get "/health"
    returns json

route post "/auth/token"
    inputs username:str password:str
    returns token
```

Running `molt sync` → `src/generated/routes.py`:

```python
# GENERATED by molt capy — DO NOT EDIT
# source: api.capy  library: targets/fastapi/lib.yaml

from fastapi import APIRouter, Depends, HTTPException
from sqlalchemy.orm import Session
from .models import User, Post
from .auth import get_current_user, create_token

router = APIRouter()

# ── users ──────────────────────────────────────────────────────────
@router.get("/users",    response_model=list[UserSchema])
@router.get("/users/{id}", response_model=UserSchema)
@router.post("/users",   response_model=UserSchema, status_code=201)
@router.put("/users/{id}", response_model=UserSchema)
@router.delete("/users/{id}", status_code=204)

# ── posts ──────────────────────────────────────────────────────────
@router.get("/posts",    response_model=list[PostSchema])
...

@router.get("/health")
def health(): return {"status": "ok"}

@router.post("/auth/token")
def login(username: str, password: str, db: Session = Depends(get_db)):
    ...
```

And alongside it, `src/generated/models.py` from `schema.capy` → SQLAlchemy models.

### Why this matters

Before: the user writes `routes.py` and `models.py` by hand, and when the schema
changes they manually update both files and hope nothing drifts.

After: `api.capy` and `schema.capy` are the source of truth. `molt sync` regenerates
both. The generated files are committed but never hand-edited — the comment at the top
makes that clear.

### `molt capy` subcommands

```sh
# New top-level command group
molt capy list                      # show all *.capy.toml in this project
molt capy show api                  # library path, src, out, last-generated hash
molt capy run api                   # force-regen api.capy.toml target
molt capy run-all                   # regen all targets
molt capy check targets/fastapi/lib.yaml  # validate a library file
molt capy init my-lib               # scaffold a new library skeleton
```

`molt sync` runs `capy run-all` automatically before the package install step,
same as the glue build step.

## 3. Glue drivers — YAML library instead of Go template

### Today

A user adding a Nim glue driver writes:

```yaml
# ~/.molt/glue-drivers.yaml
- lang: nim
  build_cmd: "nim c -d:release -o:{output} {server_file}"
  server_template: "~/.molt/glue-templates/nim-server.tmpl"
```

`nim-server.tmpl` is a raw Go `text/template`:

```
package main  {{/* wrong — this is Nim, but the author has to write Go template syntax */}}
{{range .Fns}}
proc {{.Name}}({{range .Args}}{{.Name}}: {{nimType .Type}}{{end}}): {{nimType .Returns}} =
{{end}}
```

The problem: `nimType` is a Go function. It doesn't exist. The author either has to
fork molt and add it to the FuncMap, or write a verbose inline type chain:

```
{{if eq .Type "i32"}}int32{{else if eq .Type "i64"}}int64{{else if eq .Type "f32"}}float32...{{end}}
```

There's no validation. A typo in the template silently produces broken Nim code.

### With Capy

```yaml
# ~/.molt/glue-drivers.yaml
- lang: nim
  build_cmd: "nim c -d:release -o:{output} {server_file}"
  server_template: "~/.molt/glue-templates/nim-server.yaml"   # ← Capy library
```

`nim-server.yaml` is a self-contained Capy library the author fully controls:

```yaml
# nim-server.yaml  (pure YAML, no Go knowledge required)
extension: nim
context:
  module: ""
  transport: "stdio"
  fns: []
  type_map:
    i32:       int32
    i64:       int64
    f32:       float32
    f64:       float64
    bool:      bool
    string:    string
    bytes:     seq[byte]
    "[]i32":   seq[int32]
    "[]f64":   seq[float64]
    "[]string": seq[string]
    json:      JsonNode

types:
  GlueType:
    options: [i32, i64, f32, f64, bool, string, bytes, "[]i32", "[]f64", "[]string", json]
  Transport:
    options: [stdio, unix_socket, tcp]

functions:
  module:
    args: [{ kind: capture, name: name, type: string }]
    run:  set context.module name
    template: ""

  transport:
    args: [{ kind: capture, name: t, type: Transport }]
    run:  set context.transport t
    template: ""

  fn:
    args:
      - { kind: capture, name: name,    type: ident }
      - { kind: capture, name: argspec, type: json }
      - { kind: literal, value: "->" }
      - { kind: capture, name: returns, type: GlueType }
    run: append context.fns { name: name, argspec: argspec, returns: returns }
    template: ""

file_template: |
  # Generated by molt glue. DO NOT EDIT.
  import json, os, strutils, net, asyncnet, asyncdispatch

  {{ range .context.fns -}}
  proc {{ .name }}({{ range .argspec }}{{ .name }}: {{ index $.context.type_map .type }}{{ if not @last }}, {{ end }}{{ end }}): {{ index .context.type_map .returns }} =
    discard  # user-implemented — replace with real body
  {{ end }}

  proc dispatch(req: JsonNode): JsonNode =
    let fn = req["fn"].getStr()
    {{ range .context.fns -}}
    if fn == "{{ .name }}":
      {{ if .argspec -}}
      result = %* {{ .name }}({{ range .argspec }}req["args"]["{{ .name }}"].{{ nimCast .type }}{{ if not @last }}, {{ end }}{{ end }})
      {{ end -}}
    {{ end -}}
    else:
      result = %* {"error": "unknown fn: " & fn}

  # stdio transport
  while true:
    let line = stdin.readLine()
    let req = parseJson(line)
    echo $dispatch(req)
```

**What changed:**
- The type map is data in `context.type_map`, not a Go function
- `GlueType` and `Transport` validate inputs before the template runs — typos fail fast
- The whole file is readable YAML; no Go template syntax, no FuncMap knowledge
- The author tests it with `molt capy check nim-server.yaml` before registering it

### What `molt glue-driver add` looks like after

```sh
molt glue-driver add nim \
    --build "nim c -d:release -o:{output} {server_file}" \
    --server-template ~/.molt/glue-templates/nim-server.yaml

# molt detects .yaml extension → uses capy.NewLibraryYAML internally
# .tmpl extension → uses existing text/template path (backward compatible)
```

## 4. What molt sync does now

The `molt sync` pipeline gains two new steps:

```
Step 1:  uv lock (resolve + install Python packages)
Step 2:  Native modules (Cython, Rust/PyO3, kernel *.molt.toml)
Step 3:  Capy targets (*.capy.toml) ← NEW
Step 4:  Transport Glue (*.molt.toml with lang key)
Step 5:  Re-write Python shims with updated PYTHONPATH
```

Step 3 output in the terminal:

```
→ capy/api: targets/fastapi/lib.yaml + api.capy → src/generated/routes.py
→ capy/schema: targets/sqlalchemy/lib.yaml + schema.capy → src/generated/models.py
✓ 2 capy target(s) generated
```

Cache behaviour: same hash-based caching as glue and kernel modules. If neither the
library file nor the source file changed, the step is skipped:

```
→ capy/api: cache hit
→ capy/schema: cache hit
```

## 5. Full project example — before and after

### Before: a FastAPI project with three models and a set of CRUD routes

```
my-api/
  moltproject.toml
  pyproject.toml
  src/
    my_api/
      main.py          ← 280 lines, hand-written
      models.py        ← 120 lines, hand-written
      routes/
        users.py       ← 95 lines, hand-written
        posts.py       ← 88 lines, hand-written
        auth.py        ← 62 lines, hand-written
```

When the schema changes, the developer updates `models.py` and then manually hunts
through `routes/` to find everything that references the changed model.

### After: same project with Capy targets

```
my-api/
  moltproject.toml
  pyproject.toml
  api.capy              ← 28 lines, hand-written  ← source of truth
  schema.capy           ← 18 lines, hand-written  ← source of truth
  api.capy.toml         ← 3 lines (library + out path)
  schema.capy.toml      ← 3 lines (library + out path)
  src/
    my_api/
      main.py           ← 45 lines (app setup, import generated modules)
      src/generated/
        routes.py       ← GENERATED (do not edit)
        models.py       ← GENERATED (do not edit)
```

`api.capy` (28 lines):

```
resource users
    columns id:int name:str email:Email created_at:datetime
    auth required
end

resource posts
    columns id:int title:str body:text author_id:int
    auth optional
end

resource comments
    columns id:int post_id:int author_id:int body:text
    auth required
end

route get "/health"
    returns json

route post "/auth/token"
    inputs username:str password:str
    returns token
```

`schema.capy` (18 lines):

```
table users
    id serial primary_key
    name varchar 255 not_null
    email varchar 255 not_null unique
    created_at timestamp default now
end

table posts
    id serial primary_key
    title varchar 500 not_null
    body text
    author_id int references users
end
```

When the schema changes, you edit `api.capy` or `schema.capy` and run `molt sync`.
Both generated files update atomically. Nothing drifts.

## 6. The complete new user surface

### New files the user writes

| File | What it is |
|---|---|
| `<name>.capy.toml` | Capy target manifest: library, src, out path |
| `<name>.capy` | DSL source for that target (what the user authors) |
| `targets/<target>/lib.yaml` | Capy library defining the grammar + templates for a target |
| `~/.molt/templates/<name>.yaml` | User-supplied `molt init` template (Capy library) |

### New commands

```sh
# Capy target management
molt capy list                               # *.capy.toml in this project
molt capy show <name>                        # library, src, out, cache status
molt capy run <name>                         # force regen one target
molt capy run-all                            # force regen all targets
molt capy check <lib.yaml>                   # validate a library file

# Scaffolding
molt capy init <name>                        # scaffold a new lib.yaml skeleton
molt template add <name> <path-to-yaml>      # register a Capy init template
molt template show <name>                    # inspect a template's prompts + outputs

# Glue driver (existing, extended)
molt glue-driver add nim \
    --build "nim c ..." \
    --server-template ~/.molt/templates/nim-server.yaml   # .yaml = Capy library
```

### What did NOT change

```sh
molt sync          # same command; Capy step is transparent
molt run demo      # unchanged
molt glue list     # unchanged
molt add / remove  # unchanged
molt build         # unchanged
```

## 7. What the migration looks like internally

The changes are additive. Nothing currently working breaks.

```
go get github.com/luowensheng/capy

internal/
  capy/
    host.go          ← capy.NewLibraryYAML wrapper; sync.Once cached libraries
    manifest.go      ← parse *.capy.toml (mirrors internal/glue/config.go)
    builder.go       ← BuildAll: hash check → capy.Run → write out file → cache
    runner.go        ← molt capy subcommand handler

internal/glue/
  codegen.go         ← detect .yaml extension on ServerTemplate → use capy host
                        detect .tmpl extension → existing text/template path

internal/syncplan/
  syncplan.go        ← add step 3 (capy.BuildAll) after native, before glue

internal/templates/
  templates.go       ← detect .yaml extension in template store → Capy library
                        directory-tree templates keep working unchanged

main.go              ← add `case "capy": err = cmdCapy(os.Args[2:])`
```

**`templates.go` detection logic:**

```go
// Existing path: directory-tree template (static files + {{name}}/{{pkg}})
if t.Source == "directory" {
    return t.applyDirectory(dir, vars)
}
// New path: Capy library template
if strings.HasSuffix(t.LibraryPath, ".yaml") || strings.HasSuffix(t.LibraryPath, ".capy") {
    return t.applyCapy(dir, vars, answers)
}
```

**`codegen.go` detection logic:**

```go
// Existing: .tmpl → text/template (backward compatible)
if strings.HasSuffix(driver.ServerTemplate, ".tmpl") {
    return generateWithGoTemplate(m, driver, buildDir)
}
// New: .yaml / .capy → Capy library
return generateWithCapy(m, driver, buildDir)
```

## Summary: what the user gains

| | Before | After |
|---|---|---|
| `molt init` prompts | None — static files | Typed prompts; conditional output; org templates |
| `molt init` validation | None — any string accepted | Types check version strings, package names, etc. |
| User-defined code generation | Not possible | `*.capy.toml` + `*.capy` in any project |
| Schema drift | Manual sync between source and generated files | `molt sync` regenerates; source and output always match |
| Custom glue driver templates | Raw Go `text/template` + FuncMap PR | YAML Capy library, no Go knowledge needed |
| `molt capy check` | — | Validate a library before registering it |

The user-facing command surface grows by one group (`molt capy`) and one manifest
type (`*.capy.toml`). Everything else is unchanged.
