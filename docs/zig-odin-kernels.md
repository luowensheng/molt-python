# Native source modules: Zig and Odin (and any C-ABI language)

## What this feature is

Today molt auto-compiles `.pyx` (Cython) and `.rs` (PyO3) source files into
Python-importable extensions. This feature extends the same drop-in-a-file
flow to **`.zig` and `.odin`** source files (and would generalise to any
language that can produce a C ABI shared library).

The user writes one source file with `export fn` (Zig) or `@(export)` (Odin)
declarations. molt compiles it to a `.so` and generates a sibling `.py`
shim that uses `ctypes` internally, so:

```python
import math_kernel
math_kernel.add(2, 3)        # → 5
math_kernel.dot(a, b, len(a))
```

works without the user ever touching `ctypes` themselves.

## Why this is the right shape

There are three plausible architectures for "native code → Python module":

| Architecture | Pros | Cons |
|---|---|---|
| **A. Real CPython extension** (Rust+PyO3, Cython) | True `import` semantics, native object marshalling, lowest overhead | Requires a per-language framework with macro support, deep Python C API knowledge |
| **B. ctypes load** (`ctypes.CDLL("foo.so")`) | Trivial to implement, no framework needed | User writes ctypes wiring by hand; not `import foo`-shaped |
| **C. ctypes load + auto-generated `.py` shim** | Looks like `import foo`, no user-side ctypes wiring, no per-language framework | Slightly higher per-call overhead than A; can't accept Python objects (lists/dicts/strings as `str`) without extra glue |

Zig has [pydust](https://pydust.fulcrum.so) — a PyO3-equivalent — but it's
pre-1.0 and uses Zig's evolving package manager. Odin has no equivalent at
all.

For both languages, **architecture C is the correct first ship**:

- Zero new framework dependencies
- Drop a `.zig` or `.odin` file and `import <name>` works
- For numerical kernels (the common case), per-call ctypes overhead is in
  the 100–200 ns range — meaningless compared to whatever native work the
  function does
- Architecture A can be added later as an opt-in (`shim = "ext"` flag)
  without breaking C-shape users

This document specifies architecture C end-to-end.

## User-facing example

User creates `math_kernel.zig` in the project root:

```zig
// math_kernel.zig
export fn add(a: i32, b: i32) i32 {
    return a + b;
}

export fn mul(a: f32, b: f32) f32 {
    return a * b;
}

export fn dot(a: [*]const f32, b: [*]const f32, n: usize) f32 {
    var s: f32 = 0;
    var i: usize = 0;
    while (i < n) : (i += 1) s += a[i] * b[i];
    return s;
}
```

User runs `molt run python main.py`:

```python
# main.py
import math_kernel
print(math_kernel.add(2, 3))                    # → 5
print(math_kernel.mul(2.5, 4.0))                # → 10.0

import ctypes
arr = (ctypes.c_float * 3)(1.0, 2.0, 3.0)
brr = (ctypes.c_float * 3)(4.0, 5.0, 6.0)
print(math_kernel.dot(arr, brr, 3))             # → 32.0
```

No `pyproject.toml` configuration required for the basic case. The same
shape works for `math_kernel.odin` with `@(export)` declarations.

## What molt actually generates

For `math_kernel.zig`, molt produces in `~/.molt/native/<hash>/`:

### `math_kernel.so`

The shared library, built by `zig build-lib -dynamic -O ReleaseFast`
(or `odin build … -build-mode:shared` for Odin). Contains the exported
functions as plain C-ABI symbols.

### `math_kernel.py`

The auto-generated ctypes shim. Looks like:

```python
# Auto-generated by molt for math_kernel.zig.
# Do not edit — regenerated on every build.
import ctypes, os

_path = os.path.join(os.path.dirname(__file__), "math_kernel.so")
_lib  = ctypes.CDLL(_path)

_lib.add.argtypes = [ctypes.c_int32, ctypes.c_int32]
_lib.add.restype  = ctypes.c_int32
def add(a, b):
    return _lib.add(a, b)

_lib.mul.argtypes = [ctypes.c_float, ctypes.c_float]
_lib.mul.restype  = ctypes.c_float
def mul(a, b):
    return _lib.mul(a, b)

_lib.dot.argtypes = [ctypes.POINTER(ctypes.c_float),
                     ctypes.POINTER(ctypes.c_float),
                     ctypes.c_size_t]
_lib.dot.restype  = ctypes.c_float
def dot(a, b, n):
    return _lib.dot(a, b, n)
```

The shim is what Python imports. It loads the `.so` exactly once when the
module is first imported.

## Pyproject.toml configuration

Default behaviour requires no config. Optional knobs:

```toml
[tool.molt.zig.kernel]
optimize = "ReleaseFast"     # ReleaseFast | ReleaseSafe | ReleaseSmall | Debug
shim     = "py"              # "py" (default) | "ext" | "none"
strip    = true              # strip symbols after compile

[tool.molt.odin.kernel]
optimize = "speed"           # speed | size | minimal | none | aggressive
shim     = "py"
```

`shim` values:

| Value | Output | Use when |
|---|---|---|
| `"py"` | `.so` + `.py` ctypes shim (default) | You want `import foo` to "just work" |
| `"ext"` | `.so` only, but built as a real CPython extension via auto-generated C glue | You need to accept Python objects (str/list/dict) directly |
| `"none"` | `.so` only, no shim | You'll do your own ctypes loading |

This document specifies only the `"py"` path. `"ext"` and `"none"` are out
of scope for the initial implementation but the `shim` field should be
parsed and validated up front.

## Implementation plan

The work breaks into seven independent pieces. Each builds on the existing
`internal/native/` infrastructure.

### 1. Discover `.zig` and `.odin` source files

**File:** `internal/native/native.go`

`Discover()` already walks `paths` for `.pyx` and `.rs` files. Extend the
extension check to include `.zig` and `.odin`. Each gets its own `Lang`
value (e.g. `"zig"`, `"odin"`).

```go
isPyx := strings.HasSuffix(p, ".pyx")
isRs  := strings.HasSuffix(p, ".rs")
isZig := strings.HasSuffix(p, ".zig")
isOdin:= strings.HasSuffix(p, ".odin")
if !isPyx && !isRs && !isZig && !isOdin {
    return nil
}
lang := "cython"
switch {
case isRs:   lang = "rust"
case isZig:  lang = "zig"
case isOdin: lang = "odin"
}
```

**Effort:** ~15 lines.

### 2. Add `BuildZigFile` and `BuildOdinFile`

**Files:** `internal/native/zig_kernel.go`, `internal/native/odin_kernel.go`

Mirror the structure of `BuildRustFile` in `rust.go`:

1. Read source content.
2. Hash content + ABI tag + platform + relevant config + a build-recipe
   sentinel (so future build-driver changes invalidate caches).
3. Cache hit → return the cached path.
4. Cache miss:
   - Create a build dir under `~/.molt/native/<lang>-build/<module>-<hash>/`.
   - Copy or symlink the source in.
   - Invoke the compiler:
     - Zig: `zig build-lib -dynamic -O ReleaseFast --name <module> -fno-emit-bin -femit-bin=<out> <source>`
     - Odin: `odin build <source> -build-mode:shared -out:<out> -o:speed`
     - On macOS, both need `-undefined dynamic_lookup` (or whatever the
       language's escape hatch is) since the `.so` doesn't reference
       libpython.
5. Move the artifact into the cache.

The Zig variant should reuse the `EnsureZig()` machinery that already
auto-installs zig under `~/.molt/toolchains/zig/<version>/`. The Odin
variant requires `odin` on PATH for now — auto-install is out of scope
because Odin doesn't ship official binary releases the way Zig does.

**Effort:** ~70 lines per language.

### 3. Parse `export fn` / `@(export)` declarations

**File:** `internal/native/sigparse.go`

Single-purpose: read source content, return a list of:

```go
type ExportedFn struct {
    Name    string
    Params  []SigType
    Returns SigType    // zero value = void
}

type SigType struct {
    Kind     SigKind  // primitive, pointer, void, unknown
    Primitive string   // "i32", "f32", "usize", "bool", "void", ...
    PointTo  *SigType  // for pointers
}
```

#### Zig parser (the easier one)

Match `export fn <name>(<params>) <return> {`, line-anchored at column 0
to avoid catching nested decls. Skip `comptime`, `inline`, attribute
decorators that aren't `export`. Param syntax is `name: type`. Return type
is everything after `)` and before `{`. `void` is the implicit return when
the function uses `;` instead of `{}` blocks but we only support
brace-delimited functions.

Type strings molt must recognise:

```
i8 i16 i32 i64 i128
u8 u16 u32 u64 u128
f16 f32 f64 f128
bool void
usize isize
c_int c_uint c_long c_ulong c_short c_ushort c_char c_void
[*]const T   [*]T
[*:0]const u8  → c_char_p (null-terminated string)
?[*]T          → POINTER(T) or None
```

Anything else → `SigKind = unknown` → fn is dropped from the shim with a
warning. Slices (`[]const T`), error unions (`!T`), generic comptime
parameters, and structs are all in this bucket.

#### Odin parser

Match `@(export[, link_name="..."])` followed by `<name> :: proc "c" (<params>) -> <ret> {`. Same primitive type table as Zig — Odin and Zig share the same C-shaped type vocabulary.

```
i8 i16 i32 i64 i128
u8 u16 u32 u64 u128
f16 f32 f64
bool
int uint                     // platform-width signed/unsigned
rawptr                       → c_void_p
^T                           → POINTER(T)
cstring                      → c_char_p
```

Without `proc "c"` calling convention, the function won't be C-ABI-callable
from ctypes; molt must drop those with a warning.

**Effort:** ~80 lines for Zig, ~70 for Odin (Odin's type syntax is simpler).

### 4. Map signature types to ctypes

**File:** `internal/native/ctypes_emit.go`

```go
func sigToCtypes(s SigType) (string, bool)
```

Returns the ctypes expression as a Go string (e.g. `"ctypes.c_int32"`,
`"ctypes.POINTER(ctypes.c_float)"`, `"ctypes.c_char_p"`) and whether the
mapping is supported. Closed-form lookup table from the type names in §3
to ctypes expressions.

`void` return → emit `restype = None` (and the wrapper function's body
is a bare call without `return`-using-the-result).

**Effort:** ~60 lines including tests.

### 5. Generate the `.py` shim

**File:** `internal/native/ctypes_emit.go` (continued)

```go
func emitShim(moduleName, soBaseName string, exports []ExportedFn) string
```

Returns the full text of `<module>.py`. Layout:

```python
# Auto-generated by molt for <source>.
# Do not edit — regenerated on every build.
import ctypes, os

_path = os.path.join(os.path.dirname(__file__), "<so_basename>")
_lib  = ctypes.CDLL(_path)

# repeated per exported fn:
_lib.<name>.argtypes = [<arg ctypes>]
_lib.<name>.restype  = <ret ctypes>
def <name>(<py-arg-names>):
    return _lib.<name>(<py-arg-names>)
```

For void returns, emit:

```python
_lib.<name>.restype = None
def <name>(<args>):
    _lib.<name>(<args>)
```

The python argument names should match the source's. If the source uses
positional names molt can't extract (`@(export) :: proc "c" (i32, i32)`),
emit `_arg0`, `_arg1`, etc.

The shim is written to `~/.molt/native/<hash>/<module>.py` next to the
`.so`.

**Effort:** ~60 lines including tests.

### 6. Wire the shim into the syspath view

**File:** `internal/syncplan/syncplan.go` and the existing artifact-staging
code (look for where Cython/Rust artifacts get linked into the per-project
view dir).

Currently the artifact mechanism only stages a single file (the `.so`).
For Zig/Odin kernels, both the `.so` AND the `.py` shim must end up in
the view dir, both alongside each other, both reachable from
`PYTHONPATH`. The shim has to import the `.so` from the same directory:
`os.path.join(os.path.dirname(__file__), "<name>.so")` — so they
*must* be in the same dir at runtime.

Implementation:
- Extend `Artifact` (or add a sibling struct) to carry an optional
  "shim" path alongside the main artifact.
- The view-staging code links/copies both files into the view dir
  whenever a shim is present.

**Effort:** ~40 lines including handling cache rehydration.

### 7. Tests

**File:** `internal/native/sigparse_test.go`,
`internal/native/ctypes_emit_test.go`

Cases the test suite must cover:

| Test | What it verifies |
|---|---|
| Zig: bare `export fn add(a: i32, b: i32) i32` | one fn, two i32, i32 ret |
| Zig: pointer + length convention | `[*]const f32` → `POINTER(c_float)` |
| Zig: void return | emit `restype = None` |
| Zig: `[*:0]const u8` | maps to `c_char_p` |
| Zig: nested `fn` ignored | indented `fn` doesn't appear in exports |
| Zig: non-`export` ignored | regular `fn` doesn't appear |
| Zig: unsupported type | logged, dropped |
| Odin: `@(export) foo :: proc "c"` | basic case |
| Odin: missing `"c"` ABI | dropped with warning |
| Odin: `cstring` ↔ `c_char_p` | mapping correct |
| Shim emission | full .py text round-trips through `ast.parse` |
| End-to-end (integration test, optional) | actual zig install → compile a real kernel → import → call |

**Effort:** ~150 lines.

## Out of scope (deliberately)

These are explicitly NOT part of this feature. Each can be added later
without breaking the design above.

- **`shim = "ext"` (CPython extension via auto-generated C glue).** The
  field is parsed and validated, but only `"py"` and `"none"` are
  implemented. Anyone setting `"ext"` gets a clear "not yet supported"
  error.
- **Odin auto-install.** `odin` must be on PATH. Once Odin ships official
  binary releases, follow the zig pattern.
- **pydust integration for Zig.** A separate, larger feature whose API
  shape would be different (proper `import`, type-checked params via Zig
  `comptime`, full Python object marshalling).
- **Struct return types and argument types.** Both languages can return
  structs by C ABI but ctypes struct definitions would need to be
  inferred, which is significantly more parser work. Out of scope.
- **String parameters as Python `str`.** ctypes only deals with bytes;
  user must pass `bytes` (or use `c_char_p` and do their own encoding
  in the shim caller). Documented limitation.
- **Multiple `.zig` / `.odin` files compiled together.** First version
  treats each source file as an independent module. Cross-file imports
  on the native side are out of scope.
- **The Odin pyproject knob spec.** Initial version reads
  `[tool.molt.odin.kernel]` but the design only has the `optimize`,
  `shim`, and `strip` fields enumerated. Extension is straightforward.

## Cache hash extension

Each new language gets its own build-recipe sentinel string mixed into
the cache hash, mirroring `rustBuildRecipeVersion`:

- `zigKernelRecipeVersion = "v1"`
- `odinKernelRecipeVersion = "v1"`

Plus the relevant config fields (`optimize`, `shim`, `strip`) so toggling
any of them rebuilds. Plus the source content. Plus the ABI tag and
platform.

The shim file does NOT need its own hash entry — it's deterministic from
the parsed signatures, which are deterministic from the source content.

## Failure modes and error UX

| User mistake | What molt should do |
|---|---|
| `zig` not on PATH and `auto_install = false` | Clear error referencing `[tool.molt.zig] auto_install` |
| `odin` not on PATH | Clear error: install Odin from `https://odin-lang.org/` |
| Source has 0 export fns | Compile and emit empty shim with a comment; `import foo` works but exposes nothing. Print a warning. |
| Source has unsupported types | Per-fn warning, fn dropped from shim. The other fns still work. |
| Source compile fails | Surface the compiler's stderr verbatim, like the existing rust/cython errors |
| Shim runtime: `.so` missing | ctypes raises `OSError`; not molt's problem (the cache layer guarantees both files together) |

## Extension: `cpython_extension` / `shim = "ext"` (future)

Once `shim = "py"` is shipped, adding `shim = "ext"` is mostly:

1. Generate a small `<module>_glue.c` from the same parsed signatures.
   It contains `PyMethodDef[]`, `PyModuleDef`, `PyInit_<module>`, and a
   thin wrapper per function that does `PyArg_ParseTuple` + native call +
   return conversion.
2. Compile the glue with the existing C compiler (zig cc or system cc)
   alongside the language-specific output. Link them together.
3. Skip generating the `.py` shim. The artifact is `<module>.so` only,
   fully importable.

Effort: ~120 lines once the signature parser exists. Worth doing if
performance-sensitive users complain about ctypes overhead, or once we
need to accept Python objects directly.

## Why this is worth doing

- **`.rs` works → `.zig` should too.** molt's value prop is "drop a file
  in your project, get a fast native module." Every native language we
  add expands the surface where this works without users assembling a
  build system.
- **Zig is genuinely better than C for many use cases.** Cleaner syntax,
  stricter semantics, no headers, comptime, integrated build system.
  Letting users write Python kernels in Zig with zero ceremony is a real
  productivity win.
- **Odin has a small but devoted user base.** Same argument, smaller
  audience.
- **The ctypes-shim pattern is the right *first* step.** It gets us to
  "drop `.zig`, get `import`" quickly without committing to one language
  framework or paying the cost of generating C glue we may not need.
